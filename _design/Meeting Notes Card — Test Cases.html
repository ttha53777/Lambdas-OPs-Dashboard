Timeline rail · chapter meetings

The notes card,
in every state it can reach

A chapter meeting's description is its minutes — the same column the Chapter page's minutes textarea writes. The rail used to dump that whole field into a one-line meta row. It now renders a dedicated block that shows the AI summary when one exists and falls back to the raw minutes when the user never asked for one. Three independent fields decide which frame you get, so there are more than two states.

description

The minutes. Can be empty, four junk characters, or 1,700 words. Editing it bumps notesUpdatedAt.

notesSummary

The AI recap. Absent until someone presses Summarize on the Chapter page — never generated automatically.

notesSummaryAt vs notesUpdatedAt

Minutes edited after the summary was made (past a 2s grace) ⇒ the summary is stale and says so.

Case 01

Nothing yet

The meeting hasn't happened, or nobody took minutes. MeetingNotes returns null — no empty card, no "no notes yet" placeholder. The rail goes straight from the meta rows to attendance. This is the majority of rows in a real chapter: 8 of the 10 meetings in the dev org have description = "".

Why no placeholder

An empty "Minutes" card on a meeting that hasn't happened is noise on the most common row in the list. The rail already tells you the meeting is in 4 days; absence reads correctly here.

Unchanged from before

This is the "UNLESS"

No summary exists because nobody pressed Summarize — not because one failed. The card must not imply the AI had a turn and declined.

Scroll, not truncate

max-height: 320px; overflow-y: auto. Truncating with an ellipsis would hide the one thing the officer opened the row to read, and the rail is already a scrolling column — a nested scroll is cheaper than a 40-screen rail.

The leading #

Raw minutes are rendered as plain text, so an ATX heading stays visible as #. Correct: this is a transcript of what someone typed, not a document to re-render. The markdown parser only runs on summaries, whose dialect the prompt pins to **bold** and - bullets.

Violet = generated

The tinted ground and the badge are load-bearing, not decoration. An officer scanning the rail must never mistake a model's paraphrase for what the secretary wrote — the timestamp names when it was produced.

Still scrolls

Even the summary exceeds 320px here. Real recaps run to ~150 words by prompt, so this is close to the worst case, and it still fits in two screens of the block.

Dialect, not markdown

The renderer handles exactly what the prompt emits: **bold**, bold-only header lines, and - bullets. Anything else falls through as a paragraph — a deliberate ceiling, not a gap.

Case 05

The summary went stale

Someone edited the minutes after the summary was generated. notesUpdatedAt now exceeds notesSummaryAt by more than the 2-second grace, so the whole block turns gold and says why. The summary is still shown — it is still mostly true, and hiding it would leave the officer with nothing.

Gold, not rose

Stale is caution, not error. Rose is reserved for overdue deadlines and destructive actions. A summary that trails its source by one edit is still the best available account of the meeting.

The 2-second grace

Summarizing writes notesSummaryAt while the last minutes edit may have landed moments earlier. Without the grace, a fresh summary would flag itself stale on the same request. Copied from the Chapter page so the two surfaces agree.

No way to act on it

The Chapter page pairs this warning with a Re-summarize button. The rail names the problem and offers no fix — you have to know to navigate to /[slug]/chapter. See the proposal in case 06.

Cost of shipping this

POST /api/ai/summarize-meeting already exists and takes only an event id. The rail would need the same busy/error handling the Chapter page has — roughly the 30 lines of summarizeNotes lifted across.

Argument against

The timeline rail is a read surface. Summarizing is authoring, and authoring minutes already lives on the Chapter page. A cross-link ("Open in Chapter") may be the more honest fix than duplicating the action.

Case 07 · open question

The minutes become unreachable

Once a summary exists, the rail shows only the summary — by design, and that is what was asked for. But the full minutes are then reachable from nowhere on this page. An officer who wants the exact wording of a motion has no path to it and no signal that a longer version exists.

Cheap and local

One useState. The minutes are already in the client as event.description — no fetch, no new endpoint. The toggle swaps the summary body for the raw body in place.

It also fixes case 05

When a summary is stale, "show full minutes" is exactly the escape hatch the officer needs — the minutes are the current truth, the summary is the trailing one.

Argument against

The brief was summary instead of notes. A disclosure control re-admits the thing that was meant to be hidden — though behind a deliberate click, not by default.

Case 08 · open question

A summary of minutes that are gone

Someone summarized a meeting, then selected the whole minutes box and deleted it. notesSummary survives — nothing clears it. The rail renders a confident violet recap of a meeting whose record is now empty, and because the block is not stale-flagged unless notesUpdatedAt moved, it may not even warn.

Rare, but it's the bad one

Every other case degrades to less information. This one degrades to information with no source — a recap presented as the meeting's record when the record was withdrawn. That's the failure worth spending a branch on.

Two lines

summary && !minutes is already computed in MeetingNotes; it only needs its own copy string. No schema change, no new field.

The other half

Arguably the summarizer should clear notesSummary when the description is emptied — a server-side fix in updateCalendar that would make this case unreachable instead of merely labelled.

What this file is asking

  1. 01
    Cases 01–05 are shipped and verified. Screenshotted against dev org lpe at /lpe/timeline?event=5 and ?event=135. Nothing here proposes changing them.
  2. 02
    Case 08 is a correctness bug, not a polish item. A summary outliving its source is the only state that shows the officer something untrue. Cheapest real fix: clear notesSummary server-side when description is emptied.
  3. 03
    Case 07 is the most-requested-shaped gap. "Show full minutes" costs one useState and the data is already client-side. It also gives case 05 its missing escape hatch.
  4. 04
    Case 06 is a judgment call about surface roles. Putting Summarize / Re-summarize in the rail duplicates an authoring action onto a read surface. A cross-link to the Chapter page may be the better answer.
